## v0.81 integration adaptations

- Retain upstream elapsed-time compensation and blocking hidraw/zero-poll-rate
  behavior. Suspended sources block on their command queue rather than sleeping
  for a possibly zero duration.
- Execute lifecycle hooks on actual command transitions, including Suspend and
  Resume received in one batch; duplicate notifications are idempotent.
- Obtain fresh fds after driver polling/lifecycle changes, without keeping borrowed
  descriptors across driver teardown. Round fd waits up and clamp before converting
  to the poll timeout type.
- Restore sensor configuration and event filters after IIO recreation. Preserve
  upstream sensor capability and unit conventions.
- Expose `use_buffer` and the already-supported `sample_rate` in the device schema.
- Preserve upstream MSI Dinput sources while adding the production IMU settings.

## Pre-existing reliability limits and hardware acceptance

These are existing production behaviors, not claims of hardware validation or
unbounded follow-on changes made during the stable migration:

1. IIO recreation waits three seconds and, if it fails, logs the failure and keeps
   no driver. It has no repeated recreation/backoff state machine.
2. Buffer refill treats all errors as no samples, including errors other than
   EAGAIN. Persistent device faults do not automatically switch to sysfs.
3. Buffer decoding assumes one signed native-endian 16/32/64-bit storage width
   across sensor channels. Mixed layouts, shifts, unsigned data and endianness
   require dedicated decoder work and representative recordings.
4. A fallback sensor sampling rate and the requested trigger rate can diverge.
   Invalid or non-finite requested rates need independent validation policy.
5. Source suspend requests are queued, not acknowledged after hardware teardown.
   A driver already in a blocking read can delay lifecycle handling; the logind
   watcher has no inhibitor or reconnect loop. The upstream systemd suspend hook
   remains present. Duplicate source hooks are guarded, but target-level ordering
   still follows upstream manager/composite behavior.
6. A missing hrtimer module/configfs trigger falls back to existing selection and
   may not recover a BMI260 with a broken hardware data-ready interrupt.
7. AMD SFH precision, MSI ISH firmware availability, actual rates and orientation,
   Ally remap persistence, and repeated hardware suspend/resume remain untested
   in the cloud. Historical device YAML comments describe earlier observations;
   they are not evidence about every current kernel or firmware.

Before deployment, record kernel/firmware and verify cold start, sysfs fallback,
20 suspend/resume cycles, actual IMU event rate, filter retention, sensor axes and
units, and Ally back-button mappings on representative hardware.
